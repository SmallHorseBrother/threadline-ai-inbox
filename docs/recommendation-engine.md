# Threadline 推荐机制

Threadline 的目标不是替用户读完几千条历史，而是把当前需要注意的内容压缩成最多 3 个可执行决定。模型负责理解语义，规则负责稳定排序，生命周期整理器负责把历史噪声移出工作区。

## 处理链路

1. **增量采集**：Codex 本地连接器和 ChatGPT 网页连接器只提交新建或发生变化的记录。
2. **语义判断**：OpenAI-compatible 模型读取有限的前 2 轮与最近 6 轮，判断是否正在运行、等待用户、等待外部、建议继续、已经完成、可作为资料或属于低价值记录。
3. **确定性排序**：系统根据状态、未读、优先级、截止日期和最近活动计算推荐分，不让模型直接决定最终名次。
4. **多样性约束**：首页最多 3 项，同一项目最多 2 项；超过 14 天且没有紧急信号的项目最多出现 1 项。
5. **生命周期整理**：旧记录分批进入活跃区、资料库或低价值归档。只有高置信度、没有人工保护且没有未读/截止日期/高优先级信号的记录才会被自动收起。
6. **领导摘要**：只基于当前活跃工作集生成总览，不让几千条历史直接占用摘要上下文。

## 排序信号

| 信号 | 作用 |
| --- | --- |
| 等待用户拍板 | 明显加分 |
| 未读 | 明显加分 |
| 已逾期或三天内到期 | 明显加分 |
| 人工高优先级 | 加分 |
| 最近两天有实质进展 | 小幅加分 |
| 等待外部条件 | 降分 |
| 超过 14 / 30 天且无紧急信号 | 逐步降分 |
| 已完成、资料库、低价值归档 | 不进入首页推荐 |

时间久本身既不代表重要，也不代表应该归档。陈旧记录只有同时存在未完成目标、明确阻塞、人工高优先级、未读或截止日期时，才应该回到优先队列。

## 为什么换更强的模型不能单独解决问题

旧版的模型只负责分类，最终排序仍会给停滞时间加分。即使换成更强的模型，只要目标函数没变，旧任务仍可能被顶到前面。v0.2.0 因此先修正排序目标、扩大有效上下文并增加项目配额，再让模型处理真正需要语义理解的部分。

DeepSeek 等低成本 OpenAI-compatible 模型适合做第一遍分类。需要更高精度时，可以用更强模型只复核低置信度或首页候选，而不是反复扫描全部历史。

## 可逆与人工优先

- “永不归档”、人工状态和人工优先级覆盖自动判断。
- 资料库与低价值归档只改变 Threadline 视图，不删除来源对话。
- 任意记录都可以恢复到“建议继续”。
- 没有模型密钥时，系统仍可依赖确定性规则工作。

后续计划是把用户的“完成、稍后、保留、归档、重新激活”反馈记录成偏好信号，形成每个人自己的轻量重排层。
